Hexo 博客工程化实战：从手动部署到自动化内容工厂

发表于2026-10-11|更新于2026-10-11|Hexo 教程
|总字数:2.9k|阅读时长:11分钟|浏览量:

本文整理自 Michael’s Blog · Hexo 博客工程化实战，并结合本站（Butterfly 主题 + hexo-deployer-git）的实际情况做了适配与补充。

为什么要把博客「工程化」？

写博客这件事，技术人通常的路径是：

  1. 本地 hexo new 创建文章
  2. Markdown 写内容
  3. hexo g && hexo d 手动部署

这条路径在只有几十篇文章时完全够用。但当文章数量突破 400+、你希望保持周更甚至日更节奏时，手动流程就会暴露出几个致命问题：

  • 部署依赖本地环境：换台电脑就写不了
  • 选题靠灵感驱动：没灵感就断更
  • SEO 全靠感觉：标题写得好不好、结构化数据有没有、sitemap 对不对，全凭手感
  • 写完就忘：哪篇文章阅读量高、哪些关键词带来流量，完全没有数据反馈

这篇文章记录的是把 Hexo 博客从「手动写作」改造成「自动化内容工厂」的完整过程，涉及四个核心模块：

  1. 自动部署：push 即发布
  2. AI 辅助选题与写作：选题池 + 多 Worker 并行生产
  3. SEO 工程化：结构化数据、自动 sitemap、内链策略
  4. 阅读量分析：数据采集 → 看板 → 反哺选题

每个模块都有可直接复用的配置和代码。

一、从 hexo deploy 到 push 即发布

1.1 两条部署路线

Hexo 的部署本质上就是把 public/ 这个目录「搬」到托管平台。常见两条路线：

路线 原理 适合
本地 push（本站当前方案） 本地构建后，hexo-deployer-git 把 public/ 强推到 Pages 仓库 文章量不大、想完全掌控本地环境
CI 构建（GitHub Actions） 仓库只存 Markdown，CI 里安装依赖、构建、发布 文章多、多人协作、想换台电脑就能写

本站用的是第一条：_config.yml 中配置 hexo-deployer-git，一条命令完成生成和部署。

注意：hexo-deployer-git 使用 .deploy_git/ 作为中转仓库，它会把 public/ 里的内容强制推送过去，所以 Pages 仓库里不需要（也不应该）保留源文件。

四、阅读量分析

写完就忘是内容创作最大的浪费。把数据采集回来，才能形成「写作 → 反馈 → 选题」的正循环。

4.1 数据采集

方案有三档，按投入从低到高：

方案 成本 数据粒度 隐私
不蒜子（busuanzi） 免费、一行代码 站点 PV/UV、单篇阅读量 第三方统计
Umami / Plausible（自托管） 一台小服务器 页面级 PV、来源、停留 数据自有
GA4 + 自定义事件 免费、配置复杂 全量行为、可做漏斗 Google

本站当前用的是不蒜子，配置在 Butterfly 的 busuanzi 开关里，零成本但粒度粗。想要按文章、按来源分析，就得换 Umami 这类自托管方案。

4.2 看板

数据落到 SQLite / Postgres 后，用 Metabase 或 Grafana 做一个最简单的看板，关注四个指标：

  • 单篇 PV/UV 排行：哪些文章真的有人看
  • 流量来源：搜索 / 直链 / 社交，各占多少
  • 搜索关键词：哪些词带来了流量（Search Console）
  • 跳出率与停留：内容是否真的被读完

4.3 反哺选题

看板的最终目的是回写进选题池：

经验： 一篇文章 PV 高，就写它的「续集 / 进阶 / 姊妹篇」——这是最省力的选题来源，因为需求已经被验证过了。

五、本站的落地清单

结合本站（Butterfly + GitHub Pages）现状，按投入产出比排序的改造顺序：

  1. 短期：在 scripts/ 里加 JSON-LD 结构化数据；补全每篇文章的 description
  2. 中期：把部署迁移到 GitHub Actions（换台电脑也能写）；接入自托管 Umami
  3. 长期：建选题池 + AI Worker 流水线；每周复盘一次看板，把高 PV 主题做成系列

一句话总结：手动部署解决「能不能发」，工程化解决「能不能持续发」。 文章数过了 100 篇，后者才是真正的瓶颈。

git push origin main

选题 → AI 写作 → git push → CI 构建 → 部署上线

这里发布到 gh-pages 分支。如果站点仓库本身就是 <user>.github.io（例如本站），对应分支要改成 main。
